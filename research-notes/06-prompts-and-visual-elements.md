# 06 · 提示词如何控制 & 画面元素是什么（小白版）

> 这两块是整套研究里最"看不见"的部分：提示词控制是**这个 skill 怎么指挥 AI 干活**，画面元素是**屏幕上那些字、卡、图到底是什么东西**。尽量用比喻讲。

---

# Part A · 提示词是如何控制、如何推进的

## 先破除一个误解

很多人以为 skill 里有个"程序"在跑流程。**没有。**

整个 web-video-presentation 里会执行的代码只有三样：`scaffold.sh`（建项目）、`extract-narrations.ts`（抽文本）、`synthesize-audio.sh`（合成音频）。**流程本身没有任何代码在控制**——控制流程的就是一堆 Markdown 文档，而"运行"这些文档的机器是 **AI 自己**。

所以"提示词控制"的本质是：**把操作手册写得足够好、并且在正确的时机只给 AI 看正确的那几页**。下面是这个 skill 用到的 6 种手法。

## 手法 1 · 触发器：AI 什么时候想起这个 skill？

每个 skill 的 [SKILL.md](../web-video-presentation/SKILL.md) 开头有一段 `description`（描述）。AI 平时"心里"装着所有 skill 的一句话简介，当你的话跟某条简介匹配上（比如你说"帮我把这篇文章做成视频"），AI 才把那份完整的 SKILL.md 读进来。

> 比喻：description 像书脊上的标签，正文平时在书架上，用到才抽出来。

## 手法 2 · 分阶段喂文档（渐进式披露）

SKILL.md 里有一张"阶段 × 必读文件"表（SKILL.md「各阶段文件读取指南」）：

| 阶段 | 必读 |
|---|---|
| 写口播稿 | SCRIPT-STYLE.md（怎么把文章改成人话）|
| 写 outline | OUTLINE-FORMAT.md（怎么切章节）|
| **写每一章（重复 N 次）** | **CHAPTER-CRAFT.md（怎么把画面做好看）** |
| 合成音频时 | AUDIO.md |
| 录屏时 | RECORDING.md |

关键设计在第二列第三行：写章节这件事一个视频要做 8~10 次，AI 干活干久了会"忘规矩"，所以规定**每写一章都必须重读一遍 CHAPTER-CRAFT.md**。这就像防止工人干久了凭手感乱来，每次开工前强制再看一眼图纸。

> 为什么不一次全给？上下文（AI 的"工作记忆"）有限。一次塞 2000 行规则，写到第五章就稀释没了。按需喂 = 每次喂的浓度都够。

## 手法 3 · 硬节点：强制刹车 + 填空模板

光有手册 AI 会想"一口气跑到底"（AI 天生倾向不问人就做完）。所以 SKILL.md 里写了几个**"必须停"的硬节点**（Checkpoint）：

- 内容写完 → 必须停下来，等用户确认 5 件事（稿子/大纲/主题/素材/开发模式）
- 第 1 章做完 → 必须停下来等用户验收
- 音频合成前 → 必须让用户确认文本

光说"停"还不够，SKILL.md 直接给了**停下来的说话模板**（「Checkpoint Plan 总结模板」）——AI 照着填空：

```
内容计划写完，产出文件：
  📄 script.md      {X} 字 / ~{T} 分钟
  📄 outline.md     {N} 章 / {M} 步
接下来一次对齐 5 件事：
  1. 稿子要不要改？…
  3. 选哪个主题？我的推荐：★ <推荐1：nameZh (id)> — 因为 <bestFor 命中>…
```

> 比喻：不只是告诉销售"要跟客户确认"，而是直接把话术单打印好递给他。

## 手法 4 · 把"质检员"也写成提示词

AI 自己检查自己，通常糊弄（"看了一遍没问题"）。所以 skill 写了**硬性自检协议**：

1. 最好：开一个**独立的审查 AI**（agent），把"产出文件 + 检查清单"递给它，要求逐项报告哪条过哪条不过、附证据
2. 次之：没有独立 agent 能力，就开一个 subagent 干同样的事
3. 兜底：都不行，才自己查——且"不允许目测一遍就放行"

还加了铁律：**"先按不合格项改完，再向用户汇报。直接拿原始结论汇报 = 违规"**。

> 本质：把"质检"从 AI 的一种态度，变成一道有角色、有清单、有追责的程序。

## 手法 5 · 并行模式的提示词配方

选了"并行开发"时，AI 会把第 2~10 章分给多个 subagent 同时写。SKILL.md 精确规定了每个 subagent 的提示词**必须包含什么**：

- 本章的 outline 段落（含信息池）
- CHAPTER-CRAFT.md 的文件路径（必须去读）
- 当前主题 theme.json 的气质描述
- 第 1 章的代码（当风格参考，不是抄袭对象）
- 硬规则：每章独立 CSS 前缀、不许改共享文件、完工必须跑类型检查

> 这是"菜单式配方"：漏一项，那一章的质量就失控。

## 手法 6 · 连命令行输出都是提示词

`scaffold.sh` 跑完会在终端打印一大段"下一步指引"（写章节必读什么、narrations.ts 是真相源、怎么录屏……）。这是给**下一个时刻的 AI** 看的——脚手架跑完时 AI 可能已经忘了细节，终端输出就是一张贴在手边的便签。

## 与 HyperFrames 的提示词控制对比

| | web-video-presentation | HyperFrames |
|---|---|---|
| 控制载体 | SKILL.md + references 文档 | 同样是 skill 文件（18 个），架构更工业化 |
| 分流方式 | 靠 AI 读懂用户意图走流程 | **路由表**：9 种成片类型（slideshow / 产品宣传片 / 口播解说…）各配一个专属 skill，入口先面谈、产出 `BRIEF.md` 作为"唯一路由凭证"，后面所有步骤只认这份 brief |
| 防遗忘 | 每章重读 CHAPTER-CRAFT | 每个步骤有 **Gate（门禁）**："上一关的产物文件不存在就停下"——用文件存在性做闸门，比"记得重读"更硬 |
| 多 AI 协作 | 并行章节的提示词配方 | "每帧派一个 subagent" + 共享的 frame-worker 角色契约文档 |
| 质检 | 自检协议（AI 审 AI） | `npx hyperframes check` 命令——**用真浏览器跑一遍，问题不过就 exit code 非零**，机器 gate 替代态度 gate |

一句话：两家都是"文档即程序"，HyperFrames 把更多闸门**从"叮嘱"升级成"文件/命令级的硬检查"**——这正是 [04-improvements.md](04-improvements.md) 建议复刻者学习的地方。

# Part B · 画面里的元素到底是什么？是模块化的吗？

## 先给全景：三层楼

屏幕上你看到的一切（大字、数字、卡片、分割线、动画、背景纹理），分三层。**从下往上，模块化程度递减、自由度递增**：

```
第 3 层 · 章节画面（每章 AI 现场手工创作）     ← 最自由，最不模块
第 2 层 · 预制零件（~20 个现成 CSS 零件）      ← 半模块
第 1 层 · 皮肤（主题 token，换一个文件全变）    ← 完全模块
        ── 地基：舞台引擎（1920×1080、点击推进、音频驱动）固定不动
```

## 第 1 层 · 皮肤：主题 token

**token = CSS 变量**，你可以理解成"调色盘 + 字体盘"上贴了标签的格子：

```css
--surface:  #1a1714;   /* 舞台底色 */
--text:     #f5f0e5;   /* 正文字色 */
--accent:   #ff4a2b;   /* 唯一的强调色（火热橙）*/
--font-display-cn: "Noto Serif SC";  /* 中文标题字体 */
```

skill 内置 23 套主题（暗色印刷 / 报社 / 粉笔黑板 / 赛博朋克 / 瑞士极简…），每套就是这样一个文件。**规矩**：写章节时颜色、字体**只准写标签，不准写具体色值**——所以换主题 = 换一个文件，所有章节自动跟着变，一行代码不用动。

皮肤还管"性格"：卡片圆不圆角（报社 0 圆角、keynote 大圆角）、分割线是 1px 发丝还是 2px 虚线、大数字是衬线斜体还是终端等宽、背景要不要纸纹/扫描线/暗角。

## 第 2 层 · 预制零件：primitive class

[base.css](../web-video-presentation/templates/src/styles/base.css) 里预制了约 20 个现成零件，每个是一个 CSS 类名，章节直接"挂"着用：

| 零件 | 长什么样 |
|---|---|
| `.hero-num` | 超大数字（"02"、"+47%"），字体风格由主题决定 |
| `.card` | 卡片（底色/边框/圆角/阴影全是主题说了算）|
| `.rule` | 分割线（粗细/实虚由主题决定）|
| `.pull-quote` | 左边带粗色条的大引用块 |
| `.kicker` / `.label-mono` | 小号等宽字母标签（"CHAPTER 01"那种）|
| `.badge-mono` | 小胶囊徽章 |
| `.dot-accent` | 发光的强调色圆点 |
| `.masthead` | 报头式的页眉行 |

关键：**零件只管"结构"，长相完全交给皮肤**。章节写 `<div class="card">`，报社会渲染成硬朗直角纸卡，keynote 会渲染成大圆角玻璃卡。

> 比喻：零件是宜家的标准板材，主题是"北欧风/工业风"的贴皮方案，章节是拼装图纸。

另有几个固定的 React 小组件：`MaskReveal`（文字划入）、`Stage`（舞台）、`ProgressBar`（隐形进度条）——属于框架，不算创作自由区。

## 第 3 层 · 章节画面：AI 现场手工创作（**这里故意不模块化**）

每一章的视觉（大标题怎么出场、数字滚不滚动、流程图怎么画）**没有模板库**，是 AI 按当章内容现写的 React + CSS。这是刻意设计：

- outline **禁止**写动画（写死 = AI 变翻译机，每条视频长一个样）
- 章节只受三重约束：① 皮肤 token（颜色字体）② 完工自检清单（字号大/留白多/逐条揭示/禁紫粉渐变禁 emoji）③ "必须有视觉演示"底线（每章至少 1~2 处 CSS/SVG/Canvas 画的动起来的东西——横条生长、节点点亮、数字滚动）

`EXAMPLES/` 目录给了 2~3 个完整章节范例，但反复警告"**是 anchor 不是模板**——看结构，别照抄"。

**模块化的答案**：框架层、皮肤层、零件层高度模块化；**创作层故意非模块化**——因为模块化的模板正是"AI 味"的来源（每条视频像同一个模子）。

## 跟 HyperFrames 的元素体系比，差在哪？

| | web-video-presentation | HyperFrames |
|---|---|---|
| 画面本体 | React 组件 + CSS | **纯 HTML 文件** + GSAP 时间线（连 React 都不要）|
| 可复用零件 | ~20 个 CSS 类（贴上就用，不可安装）| **registry 注册表**：`npx hyperframes catalog --query "标题逐行揭示"` 搜现成动效组件 → `add` 安装进项目——**真的有组件商店** |
| 组合机制 | 章节 = 扁平列表（chapters.ts 注册）| **子合成**：一个 HTML 里嵌另一个 HTML（`<template>` + `data-composition-src`），可无限套娃 |
| 设计系统 | 23 套手做主题（tokens.css）| 设计预设（frame-presets）+ 脚本把你的品牌色**确定性 remix** 进去 |
| 元素的枷锁 | 颜色字体必须走 token + 反 AI 味纪律 | 动画属性**白名单**（只许动 opacity/位移/缩放/旋转/颜色），禁时钟禁随机——为了逐帧确定性 |
| 布局哲学 | 章节自由写，框架不管布局 | **Layout Contract**：先用静态 HTML/CSS 摆好"终态"，再从终态做动画 |

**最本质的差别**：web-video-presentation 的元素只要"人看着对"就行（反正最后是真人录屏）；HyperFrames 的元素必须"**机器逐帧可复现**"（同一秒永远渲染出同一画面），所以它给每个元素上了更重的枷锁、也提供了更强的零件商店。

**给你的启发**（已写进 [04-improvements.md](04-improvements.md)）：复刻时可以学 HyperFrames 两招——① 把 primitive 零件扩充成"动效词汇表"（count-up 数字滚动 / 横条生长 / SVG 路径自绘…），chapter agent 先查表再创作，既提速又天然防"整章一种动画"；② 零件层的"主题贴皮"机制值得原样保留，这是它换主题不破的根本。

# Part C · 每个视觉细节到底谁说了算（控制矩阵）

用户自然会问：背景颜色、表格颜色、阴影、字色、卡片大小、字号、字体、动态元素的形状、对齐……**这么多维度，分别是谁定的？** 把三层楼展开成一张"权力分配表"：

## 主题说了算的（换主题会变）

| 视觉维度 | 机制（token / 类） | 说明 |
|---|---|---|
| 舞台外背景（letterbox） | `--shell` | 舞台外那圈"幕布" |
| 舞台底色 / 圆角 / 边框 | `--surface` + `--r-stage` + `--stage-border` | 主题可给舞台加 4px 黑画框（bauhaus）或大圆角（keynote） |
| 舞台阴影 | `--shadow-stage` | 纸浮感 / 偏移实色 / 内阴影，主题定性格 |
| 舞台纹理装饰 | `--surface-pattern*`（网格/扫描线/纸纹）+ `--surface-vignette`（暗角） | 主题可选启用，画在舞台上所以录屏能拍到 |
| 卡片底色 / 材质 / 圆角 / 阴影 | `.card` 类背后：`--surface-2` + `--r-card` + `--card-shadow` | "卡片长什么样"主题定（纸卡 / 玻璃卡 / 硬朗色块）|
| 文字颜色（4 级灰度） | `--text` / `--text-2` / `--text-mute` / `--text-faint` | 主文 / 副文 / 标签 / 提示 |
| 强调色（唯一饱和色） | `--accent` + `--accent-soft` / `--accent-glow`（同色相透明度变体） | 反模式里明确"第二个饱和色会打架" |
| 分割线颜色 / 粗细 / 实虚 | `--rule` + `--rule-w` + `--rule-style`，由 `.rule` 类消费 | 报社 1px 发丝、黑板 2px 虚线 |
| **表格线的颜色** | **没有专门的表格 token**——表格 = 章节 CSS 搭 + `.tr-rule` 行线类（吃 `--rule`）+ 文字 token | 即表格颜色是"间接主题化"：行线走分割线 token，格内文字走文字 token |
| 字体家族（4 个坑位） | `--font-display-cn` / `--font-display-en` / `--font-body` / `--font-mono` | 中文标题 / 拉丁标题（斜体担当）/ 正文 / 等宽；`--font-features` 管数字等宽等 OpenType 特性 |
| 大数字的性格 | `.hero-num` 类背后：`--hero-num-font/style/weight/track` | 衬线斜体（杂志）/ 等宽发光（终端）/ 粗黑（宣言），主题定 |
| 舞台留白密度 | `--stage-pad-x/y`（如 140×100 精致 vs 80×60 密集） | 全局 breathing room |
| 动效基线（软约束） | `theme.json` 的 `mood` 字段 | **不写数值**——只告诉章节"慢电影感 / 弹簧 / 利落"，具体 ms 由章节自己拍板 |

## 章节说了算的（换主题不变，按内容自由写死）

| 视觉维度 | 机制 | 说明 |
|---|---|---|
| 字号大小 | 直接写 `96px` 或用 `--t-h1` 均可 | base.css 的字阶（--t-display-1 ~ --t-micro）只约束 primitive 类自己；**章节层不强制**。唯一硬标准是自检清单"hero ≥ 80px、禁小字" |
| 卡片大小 / 间距 / 网格 | padding / gap / grid-template 按构图写死 | 尺寸不在 token 契约里 |
| **对齐样式** | flex / grid / 绝对定位全由章节写 | 框架完全不管布局对齐——这正是"每章构图可以完全不同"的原因 |
| 动画时长 / 缓动 / keyframes | 章节自由写（参考 mood） | 唯一硬约束：总时长 ≤ 该步口播时长 |
| 动态元素的**形状**（圆点、色条、图形、粒子） | 章节 CSS/SVG/Canvas 自绘形状 | 形状自由；**颜色必须走 token**（如 `.dot-accent` 发光圆点吃 `--accent`） |
| 逐步揭示的状态切换 | 章节自己的类名（ghost/active/past） | EXAMPLES 的 list-reveal 模式 |

## 框架说了算的（章节碰不到）

舞台三层缩放结构、点击推进白名单（`data-no-advance`）、隐形进度条/模式切换的显隐逻辑、音频驱动推进——这些在 hooks/components 里，章节只消费不修改。

## 执行机制：靠什么保证章节真的守规矩？

**没有 linter、没有编译期检查——全靠纪律**：CHAPTER-CRAFT 把"颜色字体必须走 token"写成红线 + 完工自检逐项过 + 自检协议（独立 reviewer agent 核查）。这是原版最脆的一环（复核确认的缺陷之一是 7 套主题连"字体必须实际加载"都没守住）。**复刻者应该把这张矩阵表直接做成 `npm run check` 的正则扫描**（详见 [04-improvements.md](04-improvements.md) 第二节）——矩阵里"主题说了算"的每一格都对应一条机器可查的规则。

# Part D · React 库 vs Vite 模板：两种形态的差异与选择

## 先分清两个词

- **React 库**（Remotion 的形态）：一个 npm 包。你**自己的**工程里 `npm install` 它，import 进来用——它提供能力（组件、动画 hook、渲染器），但项目骨架（目录结构、入口、构建配置、约定）要你自己搭。
- **Vite 模板**（web-video-presentation 的形态）：不是包，是**一整套现成工程**。`scaffold.sh` 一跑，直接吐出一个完整能跑的项目——引擎接好线、目录约定定死、npm scripts 配好、主题装好，你往里"填内容"就行。

> 比喻：**库 = 卖你一台发动机**（车壳自己造）；**模板 = 卖你一辆整车**（钥匙一拧就走，后备箱装货就行）。

## 逐项对比

| 维度 | React 库（Remotion 式） | Vite 模板（本 skill 式） |
|---|---|---|
| 上手 | 要懂 React + 会搭工程 | 会跑一条命令即可 |
| 约定在哪 | 散在文档里，靠使用者自觉 | **长在结构里**：目录名 = 章节 id = 音频目录，narrations.ts 的位置就决定了它是真相源——想接错都难 |
| 适合的场景 | 把视频能力**嵌进已有产品**（你的 App 要让用户输入文字出视频）、参数化批量生产、长期演进的代码库 | **一次一个作品**的创作流程；agent 驱动的生成（agent 最需要一个"拿来即改"的约定骨架） |
| 升级修 bug | `npm update` 全体受益 | 拷贝进项目的代码**不会自动传播**——修了模板的 bug，所有历史项目还带着旧 bug |
| 灵活性 | 任意改造（它本来就是你的依赖） | 骨架被模板定死，改造 = 脱离模板自担维护 |
| 对 AI 友好度 | 一般——AI 每次都要自己"搭骨架 + 接线"，错配风险高（少配一个 prop、目录放错层，画面就悄悄不对） | **高**——脚手架保证每次起点一模一样；坏了 `rm -rf` 重 scaffold，章节代码先拷出来再放回去，项目是一次性用品 |

## 哪种更适合（分场景）

- **做"文章/口播 → 视频"这种创作型 skill（本研究的场景）→ Vite 模板明显更合适**。理由：① agent 的可靠性来自"约定长在结构里"，模板天然满足；② 每个视频是独立一次性项目，不需要库的长期演进能力；③ 普通使用者（非程序员）只要跑得动一条命令。**原版选对了。**
- **要做视频能力的产品功能（如"用户上传文案自动出片"的 SaaS）→ 库更合适**，Remotion 的商业模式就是这个。
- HyperFrames 走了**第三条路**：连 React 都不要，产物就是一个 HTML 文件 + CLI 工具链——仪式感最低，工程化最强（lint/check/render 全命令化），代价是作者要自建一整套运行时。

## 模板形态的固有缺陷与解法

模板 = "拷贝即冻结"。本研究抓出的 9 个缺陷（MaskReveal 不动、auto 续播、GitHub 链接……）**会留在所有已 scaffold 的历史项目里**，即使上游修了。缓解办法（复刻时建议都做）：

1. **引擎保持极小 + 独立文件**（原版已是：<400 行、hooks/components 分明）——让"重新拷一遍引擎"成本趋近于零
2. scaffold 时写 `.engine-version` 标记；`npm run check` 顺手对比 skill 仓库里的最新版本号，提示"引擎有新版，重拷 hooks/ 可升级"（章节代码不动，只换引擎文件）
3. 引擎层的 bug 用**自动化门禁**兜底（check 的无头 seek pass 能当场抓出 MaskReveal 这类"动画没播"的问题）——比指望使用者读 changelog 靠谱

> 一句话：**模板赢在"约定即结构"，输在"拷贝即冻结"；用"小引擎 + 版本标记 + 自动门禁"三件套把缺点补掉，模板形态就是 agent 创作型 skill 的最优解。**

# Part E · 补充两问：音频驱动是什么？模板能不能更进一步做成 harness？

## E1 · "音频驱动"到底是什么意思

Part C 的权力表里，框架管的最后一项是"音频驱动推进"。拆开讲：

### 三种"让画面往下走"的方式

一个"自动播放"的网页演示，下一步什么时候来？有三种答案：

| 方式 | 谁说了算 | 问题 |
|---|---|---|
| **定时器** | 代码里写死"每屏 5 秒" | 屏幕内容长短不一——长屏没读完就翻页，短屏干等 |
| **动画跑完** | 等这屏的动画放完再翻 | 动画时长 ≠ 说话时长，画面和声音会越错越远 |
| **音频驱动（本 skill 的选择）** | **"这一屏的配音念完了"这个事件本身** | 没有——声音和画面天然同源 |

### 具体机制（三句话说完）

1. 每一步的口播文案被合成为一小段音频（`1.mp3`、`2.mp3`……）
2. 网页进入某一步时，就播那一步对应的音频
3. **监听"音频播完"这个事件（`audio.ended`）**——事件一响，加 200ms 呼吸垫，自动跳下一步

```
第 3 步：屏幕演出第 3 幕 + 播放 3.mp3
              │
              ▼ 3.mp3 念完了（audio.ended）
         等 200ms 喘口气
              │
              ▼
第 4 步：屏幕演出第 4 幕 + 播放 4.mp3 ……
```

### 为什么这是框架层的"权力"

因为这套推进逻辑写在 `useAudioPlayer` 这个框架文件里，章节作者（AI）**碰不到它、也不需要碰**——它不用关心"我的画面会播多久"，只要画好画。同时它带来一条**反向纪律**：音频念完就翻页，**没有"等动画跑完"的兜底**——所以章节做动画时必须保证"动画时长 ≤ 口播时长"，否则动画会被当场切断（这正是倒逼"每屏内容精炼"的机制之一）。

> 比喻：传统做法像**看稿子翻 PPT**（翻页时机猜的）；音频驱动像**卡拉 OK**——字幕/画面跟着人声走，人声停了就进下一句。这就是录屏时"音画天然同步、零后期对轨"的全部原理。

连兜底都是"音频思维"：万一音频文件缺失/播放失败，框架退化为**按字数估时**（一个字约 250 毫秒）撑着走，保证预览永远能跑完——估的也是"念这句话要多久"。

## E2 · React 不是也能做成固定模板库吗？不也能 harness 化吗？

**能。而且这个问题问到了比"模板"更高一层的形态。** 先把三个形态排开：

| 形态 | 是什么 | 例子 |
|---|---|---|
| **库（library）** | 一个 npm 包，提供能力，骨架自己搭 | Remotion |
| **模板（template）** | 一套现成工程，拷出来填空 | web-video-presentation 的 scaffold |
| **harness（脚手架协议）** | **模板 + 流程协议 + 门禁的合体**：不仅给你工程骨架，还规定"谁在什么阶段必须做什么、过不了检查不准进下一阶段" | beautiful-article、make-html-card（你的两个 skill 都已 harness 化） |

### harness 比模板多了什么

模板回答"**长什么样**"（目录、引擎、接线）；harness 额外回答"**怎么干活的流程也定死**"：

1. **Phase 化流程**：写进 SKILL.md 的固定工序（比如 0-9 步、每步一个产出物）
2. **Checkpoint**：哪些步骤必须停下等人确认
3. **自检门禁**：每步产出按 checklist 过审，不过不改完不许汇报
4. **渐进加载**：每阶段只给 AI 喂该阶段的手册
5. **主题化/组件协议**：内容层不许手写裸样式，只能用受控组件

**关键认识：harness 和 React/HTML 技术栈无关**——它是一层"用文档写成的流程控制系统"，套在模板上面。web-video-presentation **其实已经是一半个 harness 了**：它有 Phase 1-4、有 Checkpoint、有自检协议、有渐进读取表。它缺的只是最后一块——**门禁不是机器执行**（靠 AI 自觉，而不是像 `npx hyperframes check` 那样不过就 exit 非零）。

### 那"React 组件库 + harness"呢？——你的 make-html-card 已经跑通了这条路

这正是你自己的 skill（make-html-card）做过的事：**reacticle 引擎 = React 组件库**（`Article`/`Section`/`Formula`/`Table` 这些受控组件，内容层禁止手写裸 HTML）+ **harness 流程**（Phase 0-9 + Checkpoint + 组件协议）+ **Vite 模板骨架**（scaffold + 多入口构建）。所以答案是：

> **React 完全可以做成"固定模板库"，而且模板 + 组件库 + harness 可以叠起来——三层不是互斥选项，是三个可以叠加的层。**

对 web-video-presentation 的复刻启示（映射 make-html-card 的成功经验）：

| 层 | make-html-card 已验证的做法 | 映射到视频 skill |
|---|---|---|
| 模板骨架 | scaffold.sh + Vite 多入口 | scaffold.sh（原版已有，照抄结构）|
| 组件库 | reacticle 受控组件（禁裸样式）| 把 primitive 零件升级成**受控 React 组件**（`<HeroNumber>`/`<RevealList>`/`<Counter>`…），章节内容层只能用组件 + token 组合，动画语义内建在组件里 |
| harness | Phase 0-9 + Checkpoint + checklist | Phase 1-4 + Checkpoint（原版已有）+ **补机器门禁**（`npm run check`，把纪律变成 exit code）|

组件库化还顺手解决两个老问题：① MaskReveal 这类"动画没播"的 bug 修一处、所有章节生效（组件在库层，不在模板拷贝里）；② 反 AI 味可以**内建在组件默认值里**（组件天生不产生紫粉渐变/emoji），比靠 checklist 约束更硬。

**权衡照旧要说清**：组件库层一旦定型，章节自由度下降（这正是"防 AI 千篇一律"和"内容驱动创作"之间的张力）。所以推荐的切分是——**骨架/引擎/基础零件（数字滚动、列表揭示、划入）组件库化并锁死质量；"这一章怎么构图、主导动画选什么"保留给章节层自由发挥**。原版三层楼的地板和天花板各归其位，只是把地板浇筑得更硬。
